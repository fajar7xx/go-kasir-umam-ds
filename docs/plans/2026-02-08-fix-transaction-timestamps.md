# Fix Transaction Timestamp Response Issue

**Date:** 2026-02-08  
**Status:** Approved  
**Priority:** High  
**Type:** Bug Fix

## Problem Statement

The checkout endpoint returns transactions with missing/null timestamp values in the JSON response:

```json
{
    "data": {
        "id": 6,
        "total_amount": 16500,
        "details": [
            {
                "created_at": "0001-01-01T00:00:00Z",
                "updated_at": null
            }
        ],
        "created_at": "0001-01-01T00:00:00Z",
        "updated_at": null
    }
}
```

### Root Cause

The repository layer inserts data with database-generated timestamps (`DEFAULT now()`) but never retrieves them. The response is manually constructed from in-memory data that lacks these database-generated values.

**Affected Files:**
- `internal/repositories/transaction_repository.go` - Both `CreateTransaction()` and `CreateTransactionOptimal()` methods

## Database Schema Context

```sql
-- Transactions table
CREATE TABLE public.transactions (
  id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
  total_amount real NOT NULL,
  created_at timestamp with time zone NOT NULL DEFAULT now(),
  updated_at timestamp without time zone NULL DEFAULT now(),
  CONSTRAINT transactions_pkey PRIMARY KEY (id)
);

-- Transaction Details table
CREATE TABLE public.transaction_details (
  id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL,
  transaction_id bigint NOT NULL,
  product_id bigint NOT NULL,
  price real NOT NULL DEFAULT '0'::real,
  quantity integer NOT NULL DEFAULT 0,
  subtotal real NOT NULL DEFAULT '0'::real,
  created_at timestamp with time zone NOT NULL DEFAULT now(),
  updated_at timestamp without time zone NULL DEFAULT now(),
  CONSTRAINT transaction_details_pkey PRIMARY KEY (id)
);
```

**Key Points:**
- Both `created_at` and `updated_at` have `DEFAULT now()`
- PostgreSQL automatically sets these on INSERT
- We just need to retrieve them using `RETURNING` clause

## Solution Design

### Architecture Impact
- **Layer:** Repository only
- **No changes needed:** Handler, Service, Models (already correct)

### Implementation Strategy

Use PostgreSQL's `RETURNING` clause to fetch database-generated values in the same query:

```sql
-- Instead of:
INSERT INTO transactions (total_amount) VALUES ($1) RETURNING id

-- Use:
INSERT INTO transactions (total_amount) VALUES ($1) 
RETURNING id, created_at, updated_at
```

### Optimization Strategy

1. **Single query operation** - Fetch all fields including timestamps
2. **Batch operation preserved** - Keep existing `UNNEST` approach for performance
3. **Type safety** - Reconstruct structs from database values, not memory
4. **O(1) lookup** - Use existing `productMap` to add `ProductName` during scan

## Detailed Changes

### Change 1: `CreateTransactionOptimal()` - Transaction Insert

**Location:** `internal/repositories/transaction_repository.go:227`

**Before:**
```go
var transactionID int
insertTxQuery := `
    INSERT INTO transactions (total_amount, created_at)
    VALUES ($1, NOW())
    RETURNING id
`
err = tx.QueryRowContext(ctx, insertTxQuery, totalAmount).Scan(&transactionID)
```

**After:**
```go
var transactionID int
var transactionCreatedAt time.Time
var transactionUpdatedAt *time.Time

insertTxQuery := `
    INSERT INTO transactions (total_amount)
    VALUES ($1)
    RETURNING id, created_at, updated_at
`
err = tx.QueryRowContext(ctx, insertTxQuery, totalAmount).Scan(
    &transactionID,
    &transactionCreatedAt,
    &transactionUpdatedAt,
)
```

**Rationale:**
- Remove manual `created_at = NOW()` - let database default handle it
- Scan all generated values in one operation
- No additional queries needed

### Change 2: `CreateTransactionOptimal()` - Transaction Details Batch Insert

**Location:** `internal/repositories/transaction_repository.go:237-252`

**Before:**
```go
insertDetailsQuery := `
    INSERT INTO transaction_details
        (transaction_id, product_id, price, quantity, subtotal)
    SELECT * FROM UNNEST(
        $1::int[],
        $2::int[],
        $3::float8[],
        $4::int[],
        $5::float8[]
    )
`

_, err = tx.ExecContext(ctx, insertDetailsQuery,
    pq.Array(detailTxIDs),
    pq.Array(detailProductIDs),
    pq.Array(detailPrices),
    pq.Array(detailQtys),
    pq.Array(detailSubtotals),
)
```

**After:**
```go
insertDetailsQuery := `
    INSERT INTO transaction_details
        (transaction_id, product_id, price, quantity, subtotal)
    SELECT * FROM UNNEST($1::int[], $2::int[], $3::float8[], $4::int[], $5::float8[])
    RETURNING id, transaction_id, product_id, price, quantity, subtotal, created_at, updated_at
`

rows, err := tx.QueryContext(ctx, insertDetailsQuery,
    pq.Array(detailTxIDs),
    pq.Array(detailProductIDs),
    pq.Array(detailPrices),
    pq.Array(detailQtys),
    pq.Array(detailSubtotals),
)
if err != nil {
    return nil, fmt.Errorf("insert transaction details: %w", err)
}
defer rows.Close()

// Scan results and reconstruct with all database values
finalDetails := make([]models.TransactionDetail, 0, len(details))
for rows.Next() {
    var d models.TransactionDetail
    err := rows.Scan(
        &d.ID,
        &d.TransactionID,
        &d.ProductID,
        &d.Price,
        &d.Quantity,
        &d.SubTotal,
        &d.CreatedAt,
        &d.UpdatedAt,
    )
    if err != nil {
        return nil, fmt.Errorf("scan transaction detail: %w", err)
    }
    
    // Add product name from existing productMap (O(1) lookup)
    if product, exists := productMap[d.ProductID]; exists {
        d.ProductName = product.Name
    }
    
    finalDetails = append(finalDetails, d)
}

if err = rows.Err(); err != nil {
    return nil, fmt.Errorf("iterate transaction details: %w", err)
}
```

**Rationale:**
- Change from `ExecContext` to `QueryContext` to get RETURNING values
- Scan all fields including generated `id`, `created_at`, `updated_at`
- Reconstruct structs from database values (source of truth)
- Use `productMap` (already in memory) to add `ProductName`
- PostgreSQL guarantees RETURNING order matches insertion order

### Change 3: `CreateTransactionOptimal()` - Response Construction

**Location:** `internal/repositories/transaction_repository.go:265`

**Before:**
```go
// Update details with transaction ID
for i := range details {
    details[i].TransactionID = transactionID
}

return &models.Transaction{
    ID:          transactionID,
    TotalAmount: totalAmount,
    Details:     details,

```

**After:**
```go
return &models.Transaction{
    ID:          transactionID,
    TotalAmount: totalAmount,
    Details:     finalDetails,
    CreatedAt:   transactionCreatedAt,
    UpdatedAt:   transactionUpdatedAt,
}, nil
```

**Rationale:**
- Use `finalDetails` which now has complete database values
- Add transaction-level timestamps
- No manual field updates needed

### Change 4: `CreateTransaction()` - Apply Same Fix

**Location:** `internal/repositories/transaction_repository.go:26-135`

Apply the same pattern to the non-optimized method:

1. **Transaction Insert** - Add `RETURNING id, created_at, updated_at`
2. **Detail Inserts** - Change loop to collect RETURNING values
3. **Response** - Include all timestamps

**Note:** This method inserts details one-by-one in a loop, so we'll need to scan RETURNING for each iteration.

**Implementation approach:**
```go
// Inside the loop for each detail insert
insertTransactionDetailQuery := `
    INSERT INTO transaction_details
        (transaction_id, product_id, price, quantity, subtotal)
    VALUES ($1, $2, $3, $4, $5)
    RETURNING id, created_at, updated_at
`

var detailID int
var detailCreatedAt time.Time
var detailUpdatedAt *time.Time

err = tx.QueryRowContext(ctx, insertTransactionDetailQuery,
    details[i].TransactionID,
    details[i].ProductID,
    details[i].Price,
    details[i].Quantity,
    details[i].SubTotal,
).Scan(&detailID, &detailCreatedAt, &detailUpdatedAt)

// Update the struct with database values
details[i].ID = detailID
details[i].CreatedAt = detailCreatedAt
details[i].UpdatedAt = detailUpdatedAt
```

## Performance Considerations

### Impact Analysis
- ✅ **No additional queries** - Using RETURNING in existing queries
- ✅ **Batch operations preserved** - Still using UNNEST for bulk insert
- ✅ **Minimal overhead** - ProductName lookup is O(1) with existing map
- ✅ **Memory efficient** - Pre-allocated slices with correct capacity

### Query Count Comparison

**Before & After (same):**
- 1 SELECT (batch products with FOR UPDATE)
- 1 UPDATE (batch stock update)
- 1 INSERT (transaction)
- 1 INSERT (batch details via UNNEST)

**No performance degradation** - we're just retrieving more data from existing queries.
